# 1. Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя платформу для вычислений с выдачей текстовых отчётов, которые сохраняются на диск. 
Взаимодействие с платформой осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы выведите в мониторинг и почему?

### CPU Utilization (Использование ЦПУ):

Почему: Вычисления загружают ЦПУ, поэтому важно отслеживать его использование, чтобы избежать перегрузки.

Метрика: cpu_usage_percent.

### Memory Usage (Использование RAM):

Почему: Вычисления могут потреблять много оперативной памяти, что может привести к замедлению работы или сбоям.

Метрика: memory_usage_percent.

### Disk Space (Свободное место на диске):

Почему: Отчеты сохраняются на диск, поэтому важно следить за свободным пространством.

Метрика: disk_free_space.

### HTTP Request Rate (Частота HTTP-запросов):

Почему: Платформа взаимодействует по HTTP, поэтому важно отслеживать количество запросов.

Метрика: http_requests_total.

### HTTP Response Codes (Коды ответов HTTP):

Почему: Необходимо отслеживать количество успешных (2xx), клиентских (4xx) и серверных (5xx) ошибок.

Метрика: http_requests_2xx, http_requests_4xx, http_requests_5xx.

### Response Time (Время ответа):

Почему: Важно отслеживать задержки в обработке запросов.

Метрика: http_request_duration_seconds.

2. Менеджер продукта, посмотрев на ваши метрики, сказал, что ему непонятно, что такое RAM/inodes/CPUla. Также он сказал, что хочет понимать, насколько мы выполняем свои обязанности перед клиентами и какое качество обслуживания. Что вы можете ему предложить?

### SLA (Service Level Agreement):

Метрика: Процент успешных запросов (2xx) от общего числа запросов.

Формула: summ_2xx_requests / summ_all_requests * 100.

### Error Rate (Частота ошибок):

Метрика: Процент запросов с ошибками (4xx и 5xx) от общего числа запросов.

Формула: (summ_4xx_requests + summ_5xx_requests) / summ_all_requests * 100.

### Uptime (Время доступности):

Метрика: Процент времени, когда система была доступна.

Формула: uptime_seconds / total_seconds * 100.

### Request Latency (Задержка запросов):

Метрика: Среднее время ответа на запросы.

Формула: avg(http_request_duration_seconds).

### User Satisfaction (Удовлетворенность пользователей):

Метрика: Количество жалоб или обращений в поддержку.

3. Вашей DevOps-команде в этом году не выделили финансирование на построение системы сбора логов. Разработчики, в свою очередь, хотят видеть все ошибки, которые выдают их приложения. Какое решение вы можете предпринять в этой ситуации, чтобы разработчики получали ошибки приложения?

Если финансирование на сбор логов отсутствует, можно использовать следующие решения:

### Локальное хранение логов:

Настройте ротацию логов на серверах (например, с помощью logrotate).

Разработчики могут получать доступ к логам через SSH.

### Отправка логов в бесплатные облачные сервисы:

Используйте бесплатные планы облачных провайдеров (например, AWS CloudWatch Free Tier, Google Cloud Logging).

Настройте отправку логов через агенты (например, Fluentd, Filebeat).

### Самописное решение:

Настройте сбор логов в централизованное хранилище (например, Elasticsearch + Kibana) на собственных серверах.

Используйте открытые инструменты, такие как Graylog.

5. Опишите основные плюсы и минусы pull и push систем мониторинга.

### Pull-модель:
Плюсы:

Централизованное управление сбором данных.

Легко масштабируется.

Подходит для мониторинга динамических сред (например, Kubernetes).

Минусы:

Требует доступа к целевым системам для сбора данных.

Может пропускать данные, если целевая система недоступна.

### Push-модель:
Плюсы:

Целевые системы сами отправляют данные, что упрощает настройку.

Подходит для мониторинга в изолированных сетях.

Минусы:

Требует больше ресурсов на целевых системах.

Сложнее масштабировать.

### Гибридная модель:
Сочетает преимущества обеих моделей.

9. Изучите список [telegraf inputs](https://github.com/influxdata/telegraf/tree/master/plugins/inputs). 
Добавьте в конфигурацию telegraf следующий плагин - [docker](https://github.com/influxdata/telegraf/tree/master/plugins/inputs/docker):
```
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

Дополнительно вам может потребоваться донастройка контейнера telegraf в `docker-compose.yml` дополнительного volume и 
режима privileged:
```
  telegraf:
    image: telegraf:1.4.0
    privileged: true
    volumes:
      - ./etc/telegraf.conf:/etc/telegraf/telegraf.conf:Z
      - /var/run/docker.sock:/var/run/docker.sock:Z
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
```

После настройке перезапустите telegraf, обновите веб интерфейс и приведите скриншотом список `measurments` в 
веб-интерфейсе базы telegraf.autogen . Там должны появиться метрики, связанные с docker.
